# Роадмап: замена LeadHit тремя email-триггерными сервисами (groster.me)

**Сервисы:** Best Offer · Брошенная корзина · Постпродажа
**Документ:** технический план разработки по этапам, для команды и заказчика.

---

## 0. Контекст и рамки

**Цель:** заменить внешний LeadHit собственными сервисами, реализовав только 3 сценария, дающих **82,8% дохода** от триггерных рассылок (9,5 млн ₽). Остальные (Прошлый заказ, Неактивные, Брошенный просмотр, Смартоффер, Welcome) — вне объёма.

**Ключевое ограничение заказчика (определяет всю архитектуру):**
> Без ML и без сбора поведения на сайте (просмотры, клики). Единственный источник релевантности — внешний фид «топ-5 товаров по категории», который заказчик обновляет сам.

Это осознанное упрощение: CTR/конверсия могут просесть относительно LeadHit — это **ожидаемо и не является дефектом** (см. оговорку ТЗ 2.7). На пилоте подтверждаем, а не считаем ошибкой.

### Три сервиса — сводка

| Сервис | Доля дохода | Тип триггера | Подбор | Тайминг | Конверсия (бенчмарк) | Сложность |
|---|---|---|---|---|---|---|
| **Best Offer** | 38,8% | Плановый (cron, батч раз/сутки) | Ротация категорий + топ-5, дедуп | 30 дней; 20 дней после покупки | 1,71% | Средняя |
| **Брошенная корзина** | 26,9% | Событийный, near-real-time | Товары из самой корзины | ≤5–10 мин после ухода; кап 1/3 суток | **19,83%** (самая ценная) | Высокая |
| **Постпродажа** | 17,1% | Отложенный (delayed job) | Категория дорогого товара → топ-5 | +7 дней после заказа | 17,05% | Низкая |

### Стек (дефолт, подтвердить)

PostgreSQL (данные + очереди через `SKIP LOCKED`, отдельный брокер не нужен на ~12–13 тыс. писем/мес), backend на языке магазина, ESP — российский под 152-ФЗ и доставляемость на рынке РФ (Unisender / Sendsay / Mindbox-transactional). Всё ниже стеко-независимо.

### Последовательность этапов

```
Этап 0  Инфраструктура и контракты  (фундамент)
Этап 1  Постпродажа                 (MVP, обкатка)
Этап 2  Best Offer                  (ротация + дедуп)
Этап 3  Брошенная корзина           (session-ping, near-real-time)
Этап 4  Аналитика + пилот           (сравнение с бенчмарком LeadHit)
```

## Этап 0 — Инфраструктура и контракты

Фундамент для всех трёх сервисов. Делается до первого письма.

### 0.1 Контракты фидов (согласовать с заказчиком ПЕРВЫМ — блокирует всё)

**Фид «топ-5 по категориям»:**
```
category_id | position(1..5) | product_id | updated_at
```
Уточнить: формат (JSON/CSV), транспорт (pull по URL / push), частота, поведение при пустой/устаревшей категории, дата актуальности (старый фид → не слать мусор).

**Каталог товаров (product feed):**
```
product_id | name | price | image_url | category_id | product_url | in_stock
```
Синхронизация раз/сутки. `in_stock=false` → товар не в письме.

**Заказы** (view/реплика существующей БД магазина, нового сбора нет):
```
order_id | user_id | email | order_date | status | items[{product_id, category_id, price, qty}]
```

### 0.2 Схема БД (ядро)

```
subscribers
  user_id (PK) | email | is_unsubscribed | consent_at
  last_purchase_category_id        -- старт ротации Best Offer
  rotation_pointer_category_id     -- следующая категория в очереди
  last_sent_best_offer_at
  last_sent_cart_at
  last_sent_postsale_at
  last_any_trigger_at              -- антидубль

products            -- зеркало каталога
  product_id (PK) | name | price | image_url | category_id | product_url | in_stock

top5_by_category    -- зеркало фида заказчика
  category_id | position | product_id | updated_at

categories          -- справочник в ФИКСИРОВАННОМ порядке (для юзеров без покупок)
  category_id | sort_order

email_log           -- сердце дедупликации и аналитики
  id | user_id | service (best_offer|cart|postsale)
  category_id | product_ids[]      -- дедуп Best Offer
  order_id                          -- Постпродажа: 1 письмо на заказ
  status (queued|sent|delivered|opened|clicked|bounced|unsubscribed)
  sent_at | delivered_at | opened_at | clicked_at
  attributed_order_id | revenue     -- атрибуция дохода (постфактум)

send_queue          -- очередь (PG + SKIP LOCKED)
  id | user_id | service | payload | run_after | state | attempts | locked_at

cart_sessions       -- только для Брошенной корзины (см. Этап 3)
  session_id (PK) | user_id | email | cart_items[] | cart_hash
  last_ping_at | state (active|departed|converted|sent) | created_at
```

Один `email_log` закрывает дедуп Best Offer, антидубль между сервисами и всю аналитику раздела 6. Отдельных таблиц не плодим.

### 0.3 API-контракт data-инженер ↔ разработчик

Data-инженер отдаёт **готовые выборки**, разработчик их шлёт. Вся логика отбора — на стороне выборки, разработчик её не дублирует.

```
GET /recipients/best-offer?date=YYYY-MM-DD
  -> [{ user_id, email, current_category_id, top5_product_ids[], exclude_product_ids[] }]
     (отфильтровано: 30/20 дней, не отписан, нет триггера за 24ч)

GET /recipients/postsale?date=YYYY-MM-DD
  -> [{ user_id, email, order_id, cross_sell_category_id, top5_product_ids[], already_bought[] }]
     (наступил 7-й день, заказ не отменён)

POST /email-log { user_id, service, category_id, product_ids, order_id, status }
  -> факт отправки; здесь же двигается rotation_pointer
```

### 0.4 Доставляемость (запускать в день один — прогрев идёт неделями)

- DKIM + SPF + DMARC на домене отправки.
- Отдельный поддомен для триггеров (`mail.groster.me`), чтобы не жечь основной.
- Постепенный прогрев IP/домена.
- Мониторинг репутации (postmaster, доля спам-жалоб).
- SLO доставляемости: 90–97% (по бенчмарку).

### 0.5 Email delivery модуль (общий)

- Шаблонизатор: один макет с блоками (шапка, товарный блок 1–5 карточек, футер с обязательной отпиской).
- Интеграция с ESP: отправка + вебхуки (delivered/open/click/bounce/unsubscribe) → апдейт `email_log`.
- Трекинг: open-пиксель + UTM (`utm_source=trigger&utm_campaign={service}`) — трекинг **письма**, не поведения на сайте (подтвердить с заказчиком).
- Отписка: моментально `is_unsubscribed=true` → исключение из всех трёх сценариев.

### 0.6 Логирование + скелет KPI-дашборда

6 метрик прямо из `email_log` в разрезе сервиса (см. Этап 4).

### DoD Этапа 0
- [ ] Форматы обоих фидов согласованы с заказчиком
- [ ] Схема БД развёрнута, зеркала наполняются по расписанию
- [ ] DKIM/SPF/DMARC настроены, тест ≥9/10 (mail-tester)
- [ ] ESP подключён, вебхуки пишутся в `email_log`
- [ ] Ссылка отписки снимает из всех сценариев
- [ ] KPI-дашборд показывает метрики по тестовым отправкам

## Этап 1 — Постпродажа

Самый простой сценарий: отложенное письмо +7 дней, обкатывает инфраструктуру.

### 1.1 Триггер и жизненный цикл
```
Заказ создан
  └─> INSERT send_queue(service=postsale, order_id, user_id,
                        run_after = order_date + INTERVAL '7 days', state=scheduled)

Воркер (cron раз в 5–15 мин):
  SELECT ... WHERE service='postsale' AND state='scheduled' AND run_after <= now()
  FOR UPDATE SKIP LOCKED
  └─> проверки (1.4) → подбор (1.3) → отправка → email_log
```
7 дней — настраиваемый параметр.

### 1.2 Данные
Заказ (`items`, `order_date`, `email`, `status`), `top5_by_category`, `products`. Нового сбора нет.

### 1.3 Алгоритм cross-sell (ТЗ 4.4)
```
1. Заказ из нескольких категорий → категория самого дорогого товара.
2. cross_sell = top5_by_category[этой категории].
3. Исключить product_id, уже купленные в этом заказе.
4. Пусто / фид устарел → фолбэк: категория 2-го по цене; если и там пусто → НЕ слать,
   залогировать skip (критерий 4.8: блок не пуст).
```

### 1.4 Проверки — в момент ОТПРАВКИ, не постановки
- [ ] Заказ не отменён/возвращён (актуальный `status`)
- [ ] Email не отписан
- [ ] Дедуп серии заказов (1.5)
- [ ] Антидубль: уступает Корзине в один день

### 1.5 Правило серии заказов (детализация неоднозначного ТЗ 4.2)
| Ситуация | Действие |
|---|---|
| Один заказ | 1 письмо на +7 дней |
| Заказ B <7 дней после A (обе задачи ждут) | Гасим A, шлём по B |
| Заказ B >7 дней после A | Письмо по A ушло — B порождает свою задачу |

### 1.6 Структура письма (ТЗ 4.6)
Благодарность + детали заказа · блок cross-sell (картинка/название/цена/кнопка/UTM) · отписка в футере.

### DoD Этапа 1 (ТЗ 4.8)
- [ ] Письмо стабильно на 7-й день без ручного запуска
- [ ] Отменённые/возвращённые заказы не порождают отправку (проверка на отправке)
- [ ] Cross-sell не пуст и не повторяет купленное
- [ ] Правило серии заказов работает на кейсах <7 и >7 дней
- [ ] Постпродажа уступает Корзине в один день
- [ ] Все статусы в `email_log` и на дашборде

**Акцент:** все проверки актуальности — в момент отправки, не постановки. За 7 дней заказ отменяют, клиент отписывается или делает новый заказ.

## Этап 2 — Best Offer

Плановая рассылка, самая доходная. Сложность — в ротации категорий и дедупе.

### 2.1 Триггер: батч раз/сутки
```
Cron (раз/сутки):
  1. Выборка кандидатов (2.2) — эндпоинт data-инженера
  2. Подбор по ротации (2.3)
  3. send_queue (state=queued)
  4. Воркер отправки → email_log → сдвиг указателя ротации
```

### 2.2 Условие отправки (ТЗ 2.2)
```
- есть email И не отписан
- наступил таймер:
      last_sent_best_offer_at + 30 дней <= сегодня       (обычный цикл)
      ИЛИ last_purchase_at + 20 дней <= сегодня           (сброс после покупки)
      — покупка ПЕРЕБИВАЕТ 30-дневный таймер
- НЕ получал НИ ОДНОГО триггера за 24 ч                   (антидубль)
```

### 2.3 Ротация + дедуп (ядро, ТЗ 2.4)
```
1. Категория = rotation_pointer_category_id
      дефолт: last_purchase_category_id, иначе categories[sort_order=1]
2. items = top5_by_category[категория]
3. Дедуп: исключить product_id из последних 2–3 писем Best Offer (email_log)
4. Если осталось < 2 товаров:
      → следующая категория (по sort_order, циклично) → повтор с шага 2
      → лимит попыток = число категорий (защита от бесконечного цикла)
5. Отправить; ПОСЛЕ отправки:
      → rotation_pointer := следующая категория
      → записать product_ids + category_id в email_log
```
**Акценты:** указатель двигается только после успешной отправки; лимит попыток защищает «выжженного» дедупом юзера.

### 2.4 Нагрузка
~12–13 тыс. писем/мес ≈ 400–430/день. Оптимизаций не требует.

### 2.5 Антидубль (низший приоритет: Корзина > Постпродажа > Best Offer)
```
если сегодня уже есть/запланирован другой триггер
      → Best Offer НЕ ставим
      → last_sent_best_offer_at НЕ сдвигаем (иначе юзер теряет цикл)
```

### 2.6 Структура письма (ТЗ 2.6)
Тема + вступление · блок 5 товаров категории (картинка/название/цена/кнопка/UTM) · отписка.

### DoD Этапа 2 (ТЗ 2.8)
- [ ] Автоотправка по расписанию 30/20 дней без ручного вмешательства
- [ ] Подборка различается между письмами одному юзеру (проверить серию 3–4 писем)
- [ ] Указатель двигается только после успешной отправки
- [ ] Пропуск по антидублю не сбрасывает 30-дневный таймер
- [ ] Дедуп исключает товары из последних 2–3 писем
- [ ] Переход к следующей категории при <2 товарах
- [ ] Статусы в `email_log` и на дашборде

**Оговорка (ТЗ 2.7):** бенчмарк LeadHit достигнут с ML. Упрощённая ротация может дать CTR/конверсию ниже — ожидаемо. На пилоте держим доставляемость и open rate (от алгоритма не зависят), по CTR/конверсии смотрим тренд.

**Акцент:** транзакционная связка «отправил → сдвинул указатель → записал лог». Перестановка ломает ротацию или дедуп.

## Этап 3 — Брошенная корзина

Самый ценный (19,83%) и технически сложный. Делать последним.

### 3.1 session-ping (ядро, ТЗ 3.4) — единственный новый сбор данных
```
Фронтенд (JS-сниппет):
  - пока вкладка активна и корзина НЕ пуста:
        POST /cart-ping каждые 30–60 сек
        { session_id, user_id|email(если известен), cart_items[], cart_hash }
  - НЕ шлём: просмотры, клики, историю навигации
Бэкенд:
  - апдейт cart_sessions: last_ping_at, состав корзины
```
Сниппет намеренно тупой: один таймер, один POST. Без аналитики поведения (152-ФЗ + требование заказчика).

### 3.2 Детект ухода + grace-period (ТЗ 3.4)
```
Воркер (каждые ~30–60 сек):
  active И now()-last_ping_at > 3 мин   → state=departed, departed_at=now()
  departed И now()-departed_at > grace(1–2 мин) И не вернулся
        → проверки 3.3 → near-real-time очередь
```
Два порога: `3 мин` = кандидат, `+grace` = подтверждённый уход. Новый ping в grace → снова `active` (ложная тревога отсечена).

### 3.3 Проверки перед постановкой
```
- корзина не пуста
- email известен (3.4) — иначе skip
- заказ НЕ оформлен (в т.ч. «в 1 клик»)
- частотный кап: last_sent_cart_at + 3 суток <= now()
- не отписан
```

### 3.4 Идентификация анонима (пробел ТЗ — фиксируем)
| Источник email | Приоритет |
|---|---|
| Залогинен | 1 |
| Ввёл email на шаге оформления/подписки в сессии | 2 |
| cookie ↔ прошлая идентификация | 3 |
| Неизвестен | сессия не порождает письмо |

Согласовать с заказчиком — напрямую определяет охват.

### 3.5 Отмена при заказе (ТЗ 3.2) — двойная проверка
```
1. при постановке в очередь
2. ПОВТОРНО перед send через ESP
```
Гонка «письмо vs заказ»: заказ в окне между постановкой и отправкой → отмена.

### 3.6 Near-real-time отправка
```
departed+grace → send_queue (high priority)
воркер разбирает НЕПРЕРЫВНО (не батч)
цель: ≤5–10 мин после ухода
бюджет: 3 мин детект + 1–2 мин grace + очередь/рендер/ESP
```

### 3.7 Приоритет (высший: Корзина > Постпродажа > Best Offer)
Перебивает остальные в один день. Кап 1/3 суток соблюдается независимо, включая несколько уходов подряд (2-й уход в 3 суток письма не порождает).

### 3.8 Структура письма (ТЗ 3.5)
Персонализированный текст + товары **из корзины** (подбор не нужен) · прямая ссылка на корзину/оформление с восстановлением состава + UTM · опционально промокод (источник/условия — у бизнеса).

### DoD Этапа 3 (ТЗ 3.7)
- [ ] Задержка «уход → письмо» ≤5–10 мин (замер на пилоте)
- [ ] Кап 1/3 суток, включая несколько уходов подряд
- [ ] Отмена при заказе до фактической отправки (двойная проверка)
- [ ] Grace отсекает ложные уходы (свёрнутая вкладка/обрыв сети)
- [ ] Аноним без email не порождает письмо
- [ ] Конверсия на пилоте ≥15% (порог от 19,83%)
- [ ] Статусы в `email_log` и на дашборде

**Акценты (частые точки поломки):** grace-period (иначе спам при сворачивании вкладки); двойная проверка заказа (иначе «забыли корзину» уже купившему); идентификация анонима (тихо определяет реальный охват).

## Этап 4 — Аналитика и пилот

Превращает `email_log` в управленческую картину. Отвечает на вопрос заказчика: «замена не хуже LeadHit?».

### 4.1 Атрибуция дохода (фундамент)
```
clicked (вебхук) → заказ этого email в окне 72 ч → email_log: attributed_order_id, revenue
Правила:
  - несколько кликов → last-click
  - один заказ = одно письмо (не задваиваем)
  - окно атрибуции — параметр (72 ч дефолт)
```

### 4.2 Расчёт 6 метрик (единый источник — email_log)
| Метрика | Формула |
|---|---|
| Доставляемость | delivered / sent |
| Open rate | opened / delivered |
| CTR | clicked / delivered |
| Конверсия в заказ | attributed_orders / delivered |
| Unsub rate | unsubscribed / delivered |
| Средний чек | Σ revenue / attributed_orders |

### 4.3 KPI-дашборд (ТЗ 6)
Таблица «наш показатель vs бенчмарк LeadHit» + цветовая индикация:
```
🟢  в пределах бенчмарка
🟡  просадка 20–30% — наблюдение
🔴  просадка >20–30% — СИГНАЛ ревизии
```
Фильтры: период, сервис, пилот vs общая база.

**Бенчмарк LeadHit (дек.2024 – сен.2025):**
| Сервис | Достав. | Open | CTR | Конверсия | Unsub | Средний чек |
|---|---|---|---|---|---|---|
| Best Offer | 97,1% | 8,7% | 0,56% | 1,71% | 0,07% | ≈5 667 ₽ |
| Брошенная корзина | 90,7% | 13,5% | 2,86% | 19,83% | 0,31% | ≈5 656 ₽ |
| Постпродажа | 93,1% | 9,6% | 0,60% | 17,05% | 0,11% | ≈5 228 ₽ |

### 4.4 Триггер ревизии — разведение причины по слоям
| Просела метрика | Слой | Куда смотреть |
|---|---|---|
| Доставляемость | Инфраструктура | DKIM/SPF/DMARC, репутация, спам-жалобы |
| Open rate | Тема / тайминг | A/B темы, время отправки |
| CTR / Конверсия | Релевантность | Актуальность фида, ротация, дедуп |

По CTR/конверсии Best Offer и Постпродажи держим оговорку ТЗ 2.7 (без ML просадка ожидаема). Доставляемость и open rate — жёстко на уровне бенчмарка.

### 4.5 Пилот
```
- группа: 10–20% базы, помечена флагом
- период: ≥1 полный цикл Best Offer (30 дней)
- контроль: 4 периода LeadHit (дек.2024–сен.2025)
- критерии:
      Корзина: конверсия ≥15%
      Best Offer / Постпродажа: доставляемость+open на уровне бенчмарка,
                                CTR/конверсия — тренд, не точное совпадение
```

### 4.6 Админ-панель (ТЗ 8.1)
- Настройки сервисов: интервалы (30/20/7), cooldown корзины (3 суток), grace, вкл/выкл.
- Логи и статусы: `email_log`, фильтры, причины skip.
- KPI-дашборд.
- Ручной запуск/остановка.
- Мониторинг актуальности фидов (когда обновлялись, устаревшие категории).

## Критические инженерные акценты (по этапам)

1. **Постпродажа:** проверки актуальности — в момент отправки, не постановки.
2. **Best Offer:** транзакционная связка «отправил → сдвинул указатель → записал лог».
3. **Корзина:** grace-period + двойная проверка заказа + идентификация анонима.
4. **Аналитика:** дашборд отвечает «где и что чинить», а не «хорошо/плохо».
5. **Сквозное:** просадка конверсии без ML — ожидаема; просадка доставляемости — авария. Различать.
